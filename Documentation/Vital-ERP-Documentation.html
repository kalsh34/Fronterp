1. 🏢 What is this project? (The simple story)

Imagine a security company in Ethiopia called Vital Security PLC.

This company has about 227 guards who stand guard at banks, shops, and buildings. It also has office staff — the people who sit at desks and do paperwork.

Every month, the company must pay all these people. That sounds easy, but it is NOT:

  • Guards don't get a fixed salary — they get paid by the hour, and hours change every month.
  • If a guard works extra hours (overtime), they must be paid 1.5× more per hour.
  • If they work on a holiday, they get 2× more.
  • Office staff get a fixed monthly salary, but if they miss days, money is subtracted.
  • The government wants income tax and pension money taken out (7% from the worker, 11% from the company).
  • Some workers have loans that must be deducted.
  • And very importantly: no single person is trusted with money. One person prepares the payroll, another checks it, another approves it, and only then does Finance send it to the bank. This is called maker–checker.

Before this app, all of that was done in Excel files 😫. This project replaces the Excel chaos with one website where everyone does their part.

So in one sentence:

💡 One sentence Vital-ERP is a website that tracks guards and their working hours, calculates everyone's salary automatically (with tax, pension, overtime, and loans), and walks each salary through a chain of approvals before the money is paid.

2. ⚙️ How the system works inside

Think of the system like a restaurant:

  • The Frontend (React) is the dining room — the pretty part you see and click.
  • The Backend (Express API) is the kitchen — it does the real work (calculations, rules, permissions).
  • The Database (MongoDB) is the pantry — where all the information is stored forever.
┌─────────────────────┐         ┌──────────────────────┐         ┌──────────────────┐
│   FRONTEND (React)  │  /api   │  BACKEND (Express)   │ MongoDB │  DATABASE        │
│  what you see &     │ ──────▶ │  the brain: rules,   │ ──────▶ │  (MongoDB)       │
│  click, port 3000   │         │  math, security:5000 │         │  port 27017      │
└─────────────────────┘         └──────────────────────┘         └──────────────────┘

The frontend at localhost:3000 secretly forwards every /api/... request to the backend at localhost:5000 (this is configured in vite.config.ts).

The backend "brain" has three security layers

LayerFileWhat it checks

The clever "formula version" idea

👍 Nice design detail Payroll rules are stored as versions (PayrollFormulaVersion and SalaryStructure). If the government changes tax rules next year, the admin creates a NEW version with a start date — old months keep their old numbers, so past payslips never change. This is how real payroll systems do it.

Screen-by-screen guide

🏠 Dashboard (/)

Big cards for each module, a greeting ("Good morning…"), your name and role at the top right. Click a card to enter that module. Cards you're not allowed to use are simply not shown.

👥 Employees (/employees) — HR area

  1. You see a table of all employees with search/filter.
  2. Click "New Employee" → a form opens: code, names, category (GUARD or OFFICE_STAFF), phone, bank details, etc.
  3. Click an employee to open their profile → edit them, open their contract (wage, allowances, dates), upload documents (PDF/photos up to 20 MB), and manage a guarantor.

💼 Staff Attendance (/staff-attendance) — HR area

  1. Pick a period; you see the office staff list with a status per day.
  2. Mark each person: PRESENT / ABSENT / PAID_LEAVE / UNPAID_LEAVE / SICK_LEAVE / HALF_DAY / HOLIDAY / WEEKEND.
  3. HR "locks" the period when the month is done — this is required before staff payroll can be generated!

🏢 Sites (/sites) — Operations

  1. List of all sites with codes (e.g., a bank branch).
  2. New Site form: name, code, type (Commercial/Residential/Industrial/Government), address, status.
  3. Click a site → Site Detail: which guards are assigned there, plus Site Notes (digital notes/sign-offs about what happened at the site).

🪖 Guards (/guards) — Operations

List of all guards with their profiles (position: Guard or Site Leader, employment type: Permanent/Contract/Temporary, ID card number). Assign a guard's home site here.

🕒 Guard Attendance (/attendance) — Operations

This is one of the busiest screens. It includes:

  • Guard Attendance Grid — a calendar-like grid of guards × days where you enter/edit hours.
  • Guard Manual Filing — enter hours by hand when a guard forgot to clock (with an audit trail of who edited what).
  • Quick Log Panel — fast clock-in / clock-out for a guard.
  • Coverage Dashboard — "right now, is every site covered by a guard?" Red = nobody on duty!

🔄 Rotations (/rotations) — Operations

Instead of moving 50 guards one-by-one, create a rotation plan: pick guards, pick sites, pick dates — the system swaps them on schedule. Rotations have statuses: DRAFT → ACTIVE → PAUSED → ARCHIVED.

💰 Guard Payroll (/guard-payroll) — Payroll area

  1. HR/Admin picks an OPEN payroll period and clicks Generate → the system creates one DRAFT record per guard, copying their normal hours, overtime, and holiday hours from attendance.
  2. HR can edit hours or enter regular OT and holiday OT while the record is DRAFT (or RETURNED).
  3. The record is submitted → Finance checks it → it gets approved.
  4. If something is wrong, Finance clicks Return for Correction with a reason → it goes back to HR as RETURNED.
  5. After approval, Finance records the payment (method + date + reference) → status becomes PAID and an automatic journal entry is written to the accounting books.

🧾 Staff Payroll (/staff-payroll) — Payroll area

Same idea, but for office staff, and it needs the staff attendance period to be LOCKED first. Each record = contract wage − (missed days × daily rate). Workers with no active contract are skipped and listed with a reason.

🔍 Finance Review (/guard-payroll/review) — Finance

Finance's desk: see all submitted payroll records, check the numbers, check them, approve them, or return them with a reason.

🗼 Finance Control Tower (/finance)

Finance's overview: periods, totals, what's waiting for approval, what's paid.

📊 Reports (/reports)

Payroll summaries by period — who was paid what, totals for the company.

⚙️ Settings / Payroll Config / Salary Structures (/settings, /admin/...)

Admin area: manage users, tax brackets, pension rules, payroll rates, and the formula version (the recipe engine). Payroll Config is only for SUPER_ADMIN and CEO — handle with care!

👷 The Guard Portal (log in as guard@vitalpayroll.com)

When a GUARD logs in, the app becomes tiny and friendly — 5 pages only:

PageWhat the guard sees
🕐 My ShiftToday's shift: which site, what time to be there.
⏱️ My HoursHours worked this month — normal, overtime, holiday.
📍 My SitesThe site(s) they are assigned to.
💵 My PayrollTheir own payslips: gross, deductions, net pay.

The math the computer does for a guard

Normal pay    = normal hours × normal rate
Overtime pay  = OT hours × normal rate × 1.5      ← the "OT multiplier"
Holiday pay   = holiday hours × normal rate × 2.0  ← the "holiday multiplier"

GROSS   = Normal pay + Overtime pay + Holiday pay + allowances

Income tax      = looked up in the TaxBracket table (progressive: bigger
                  salary → bigger % — the exact % comes from the database)
Employee pension= 7%  (percentage from the PensionRule table)
Employer pension= 11% (the COMPANY pays this extra, not taken from the worker)
Loan            = whatever monthly amount is set on the Loan record

NET PAY = GROSS − Income tax − Employee pension − Loan − other deductions

The math for office staff

Daily rate = monthly wage ÷ 22 working days
Missed money = (ABSENT days + UNPAID_LEAVE days + ½ × HALF_DAY days) × daily rate
Basic salary = wage − missed money
then the same tax / pension / loan deductions as above.
🛡️ Safety rules built into the workflow
  • Guard payroll can only be generated while the period is OPEN.
  • Staff payroll refuses to generate unless staff attendance is LOCKED (nice clear error message included).
  • Hours/OT can only be edited in DRAFT or RETURNED status — approved records are frozen.
  • Every check/approve/pay/return step is saved in PayrollApproval + AuditLog — you can always answer "who approved this?".

8. ⚠️ Issues I found (honest list)

I read the code and ran the checks myself. Here is everything I found, worst first. 🔴 = fix before real money goes through this system, 🟠 = should fix soon, 🟡 = nice to fix.

🔴 Critical

1. The JWT secret has a weak fallback — anyone could forge login tickets In backend/src/config/env.ts, if JWT_SECRET is missing in .env, the code silently uses 'fallback-secret-change-me'. Anyone who guesses this well-known string can create valid login tokens for ANY role, including SUPER_ADMIN. Fix: fail fast at startup if JWT_SECRET is not set, instead of using a fallback.
2. MongoDB is not installed on this computer I verified: port 27017 is closed and mongod is not found. Nothing will run until MongoDB Community Server is installed. Fix: install from mongodb.com and let it run as a Windows Service.
3. Uploaded documents are served with NO login check app.ts line 50: app.use('/uploads', express.static(...)) — the folder holding employee documents (IDs, contracts, photos) is public. Anyone who knows/guesses a file URL can download it without logging in. (The upload endpoint is protected, but the files themselves are not.) Fix: serve uploads through an authenticated route.

🟠 Important

4. Same password for every demo account + it's in the source code The seed script gives all 8 accounts password123. Fine for demos — dangerous in real use. Fix: force password change on first login before going live.
5. Duplicated legacy modules — a maintenance trap backend/src/modules/ contains BOTH the hr/ tree AND older copies of the same modules at the top level (attendance/, finance/, guards/, guardPayroll/, officePayroll/, sites/, staffAttendance/, employees/…). Only the hr/ copies are wired into app.ts — the others are dead code that still compiles. A developer could fix a bug in a dead copy and see no effect. Fix: delete the unused copies.
6. Duplicate database index warnings On every startup, Mongoose warns about duplicate indexes on email, employeeCode, siteCode, and code — the schemas declare unique: true AND a manual schema.index() for the same field. Harmless but noisy. Fix: remove the redundant schema.index() lines (e.g., in Employee.ts line 80).
7. Hardcoded business numbers GUARD_MONTHLY_HOURS = 720 (payrollCalculation.service.ts) and dailyRate = salary / 22 (staff payroll) are hard-wired in code. If policy changes, a developer must edit code. Fix: move them into Settings/PayrollConfig like the tax and pension rules already are.
8. No automated tests There are PowerShell smoke-test scripts in the repo root, but no real unit/integration test suite (no Jest/Vitest). Payroll math is exactly the kind of code that needs automated tests — a wrong tax bracket would silently mispay 227 people.

🟡 Minor / housekeeping

9. Junk committed to the repository Word temporary lock files (~$tal_Security...docx), test logs (*_log.txt, tsc-check.txt, backend_err.txt) are committed. Add a .gitignore with ~$* and log patterns and remove them.
10. tsc-check.txt errors are already fixed — don't be alarmed That old file lists TypeScript errors in EmployeeList.tsx (missing selectedEmployee). I re-ran the type checker on the current code: both backend and frontend pass cleanly (0 errors). The file is just stale history.
11. CORS is wide open app.use(cors()) allows requests from any website. Fine for development; restrict it to the real frontend domain in production.
12. README is nearly empty README.md contains only "Vital-ERP / ERP". This document is a good starting point — consider copying the setup section into the README.
13. Frontend production API path The axios client uses baseURL: '/api', which only works when something proxies /api to the backend (Vite does this in dev). In production you need a reverse proxy (nginx/IIS) or a configurable API URL.
14. No rate limiting on login Anyone can try passwords forever on /api/auth/login. Add express-rate-limit (e.g., max 5 tries per minute) before going live.
15. Deep-clone caveat (this machine) The repository was cloned with --depth 1 because of unstable internet, so only the latest commit exists locally. Run git fetch --unshallow when the network is stable if you need history.
